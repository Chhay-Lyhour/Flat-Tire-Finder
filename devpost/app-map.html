FlatFinder App Map

A take-home guide to how FlatFinder works and where to start when you want to change something.

What it is

FlatFinder shows a driver in Cambodia with a flat tire the nearest repair shop for their vehicle. Drivers can also add roadside stalls that aren't on Google Maps, so the next driver can find them.

The page in the browser

Plain HTML, CSS and JavaScript in public/. A Leaflet map with OpenStreetMap tiles, the vehicle filter, the bottom panel and the add form.

The Express server

server.js and routes/spots.js. Serves the page and two routes: GET and POST /api/spots. Holds the Supabase key.

Supabase

A hosted Postgres spots table, defined in db/schema.sql. Shared by everyone, so added spots survive a refresh.

The route: one requirement from plan to screen

This follows the 30 m duplicate warning from the sentence in the plan to the behavior on screen. Search for each anchor in your editor.

  1. What was asked for

    devpost/prd.md → Adding a Repair Spot. Search: 30 m

    The plan names an exact distance and an exact message, "A repair spot is already here. Add anyway?" That turned a vague wish into a pass/fail check.

  2. How it's checked

    test/geo.test.js. Search: findNearby: keeps only spots within 30 m

    Spots about 11 m and 28 m away count. One about 400 m away doesn't. npm test re-checks this every time.

    Show the test 
    test('findNearby: keeps only spots within 30 m, nearest first', () => {
  const found = findNearby(spots, { lat: 11.5564, lng: 104.9282 }, 30);
  assert.deepEqual(found.map((s) => s.id), ['near', 'edge']);
});

  3. Where it happens

    public/js/addSpot.js. Search: function trySave

    Save runs the check first. If anything is within DUPLICATE_RADIUS_M (30), the form asks before posting.

    Show the code 
    function trySave() {
  update();
  if (saveButton.disabled) return;
  const nearby = findNearby(deps.getSpots(), point, DUPLICATE_RADIUS_M);
  if (nearby.length > 0) return showDuplicatePrompt(true);
  save();
}

A practice to reuse

Write requirements as something you could check on screen, with the exact number and the exact words.

In FlatFinder, the PRD line "within about 30 m … shows 'A repair spot is already here. Add anyway?'" became a unit test (test/geo.test.js), a single line of code (trySave in addSpot.js) and a step in the slice 2 hands-on check that passed. Nothing had to be guessed, so the agent built what was asked for the first time.

On your next project, before asking an agent to build a feature, write one sentence saying what you'd see when it works, including any numbers and the exact message. Then ask for a test that checks that sentence.
